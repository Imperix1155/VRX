## 1. The renderer's entry point: `window.vrx`

The ONLY way the renderer talks to the system. Exposed by
[`src/preload/index.ts`](../src/preload/index.ts) (typed in
[`index.d.ts`](../src/preload/index.d.ts)); every method is a thin wrapper over
one IPC channel below. The renderer is sandboxed — no other escape hatch exists
or should be added. The global is typed as `vrx?: VrxBridge` because Preview and
tests do not install the preload; every consumer must guard that absence.

Guard rule: any renderer code calling the bridge must tolerate `window.vrx`
being absent (Preview/tests) — see the query fetchers for the pattern.

The preload invoke wrapper converts the exact Electron rejection
`Error invoking remote method '<channel>': Error: rate_limited` into a local
`Error('rate_limited')`. Other invoke failures pass through unchanged.

`LoginResult.error === 'credential_persistence_failed'` means the platform
accepted sign-in but VRX could not securely save the new session. It is the one
login failure that receives dedicated renderer copy. A completed VRChat 2FA
result may instead return `auth_identity_unavailable` when the follow-up owner
refresh cannot establish a non-null account id; it remains generic. Both are
terminal: no identity or pipeline is published, and the tentative plus any
prior persisted credential is cleared from memory and durably invalidated
before best-effort physical deletion. Any failed `LoginResult`
whose main-process path discarded auth state includes `sessionCleared: true`;
the renderer must synchronously reconcile its auth cache to unauthenticated.
This marker also covers a malformed VRChat response received after installing
a replacement cookie, while preserving that response's generic error code.
Before a replacement VRChat cookie may expose a first-leg 2FA prompt, main
durably invalidates the prior account's slot; failure is terminal. A freshly
saved VRChat session keeps its established persistence state during ordinary
status refreshes, while a restored cookie performs one validated owner-binding
backfill before authenticated consumers can use it.

VRChat interactive-auth ownership is allocated when `login()` or `verify2fa()`
is requested, before its serialized body runs. A later requested operation
therefore supersedes a held earlier response at its next await fence; the held
operation cannot persist or publish its account even when the later login is
rejected. Explicit logout remains the cancellation boundary for both active and
queued operations.

## 2. IPC channels (the typed contract)

Single source: [`src/shared/ipc.ts`](../src/shared/ipc.ts) (`IpcInvoke` /
`IpcEvents`). Handlers live in [`src/main/ipc/`](../src/main/ipc/) — one file
per domain, every handler behind `isTrustedIpcSender` first.

Central registration removes electron-store's constructor-installed
`electron-store-get-data` renderer bootstrap listener (VRX never calls its
renderer initializer). electron-log uses its Node-only entry and therefore
registers neither `__ELECTRON_LOG__` channel. The registration audit enumerates
the only remaining renderer→main surface: 19 invokes and `renderer-hydrated`.

## 4. The platform adapter contract

[`IPlatformAdapter`](../src/main/services/adapters/IPlatformAdapter.ts) — what
every platform must implement. VRChat and ChilloutVR adapters are registered
per-platform in `main/app.ts`.

| Method                         | Purpose                                                                                                                                | VRChat status     |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `getAuthStatus()`              | Session check → `authenticated` / `unauthenticated` / `needs-2fa`(+method) / `error`. Clears the session on 401; keeps it on needs-2fa | ✅                |
| `login(credentials)`           | First leg; success follows secure session persistence, while `needs2fa` routes to the 2FA prompt                                       | ✅                |
| `verify2fa(code)`              | Second leg via session cookie (no password); success follows secure session persistence                                                | ✅                |
| `getFriends()`                 | `FriendRoster { friends, completeness }`; complete/partial authority is explicit, and unavailable presence rejects as degraded         | ✅                |
| `getInstanceDetails(id)`       | Full `InstanceInfo` on demand — CVR: via the VRX-59 resolver (rejects when unresolvable); VRChat: still a stub                         | CVR ✅ / VRC stub |
| `buildJoinUrl(instance, mode)` | Pure per-platform URL construction; main IPC owns validation + launch. VRChat mode is a no-op because its URI has no mode field        | ✅                |
| `selfInvite(id)`               | Invite self to a non-public instance                                                                                                   | ✅                |
| `subscribe(handler)`           | Live `AdapterEvent` stream; returns `Unsubscribe`. One shared pipeline per adapter                                                     | ✅                |

Both adapters' injected live-wiring options include `onIdentity?: (accountId: string | null) => void` (VRX-24). They publish `null` before every identity-clearing `onSessionBoundary`, so boundary callbacks cannot observe the outgoing account through `AccountSession`, then publish the current platform user id only after generation-guarded auth state settles. The VRChat data-path `AuthError` boundary is exempt because it may represent only an expired second factor and deliberately retains identity pending `getAuthStatus`. `onIdentity` feeds only `AccountSession`/registry state. The injected credential stores use `save(credential, accountId: string | null)`; after successful login, 2FA, or restore validation, adapters persist before publishing the non-null identity. Each `main/app.ts` save closure calls `saveCredential` first and records a non-null owner only if that ciphertext write succeeds. `saveCredential` revokes the old slot with an exact non-secret marker before any keychain or replacement write that can fail, so even failed best-effort deletion cannot make the prior account restorable. This is main-only state and adds no IPC or broadcast.

Interactive authentication is operation-fenced across request and body awaits.
A later direct login wins, explicit logout cancels held auth work, and automatic
invalidation of an older restored session does not cancel a newer interactive
login. VRChat additionally requires a replacement `auth` cookie before an
account-changing Basic-login response can be adopted; an existing cookie is
never rebound to a different response identity.
Every direct-login `needs-2fa` response likewise requires its own replacement
`auth` cookie, so a code can never be submitted with an older account's cookie.
Completed VRChat 2FA likewise persists only after its owner refresh supplies a
non-null account id; a failed refresh removes the tentative session and any
older persisted credential rather than retaining an unbound restart session.
While a direct-login or completed-2FA cookie is still awaiting owner validation
or secure persistence, `getAuthStatus` waits for that operation to settle and
authenticated VRChat REST entry points reject without making a request. The
first-leg `needs-2fa` state remains visible so its code prompt stays usable.
An adopted restored cookie is quarantined across Avatar, authenticated REST,
and pipeline consumers until its validated owner backfill is durably saved. A
pipeline subscriber that arrived during validation starts after that save; a
failed save clears the session without ever starting it.
The tentative fence lives on every typed adapter GET/POST.
`AuthSessionPendingError` is an `AuthError` subtype that propagates through the
friend and metadata helpers without dead-session invalidation or negative
caching. `VrcAdapter.getAuthCookieHeader()` returns `null` across the same
window, so AvatarCache's late-read provider cannot attach a tentative cookie.
Separately, paginated roster fetches check their captured session generation
before every request, and background world/group batches receive a
`canContinue` generation guard checked before every queued resolve. This stops
old-account work even after a replacement session finishes persistence, before
it can issue an old-derived request with the new account's cookie.
Both VRChat metadata resolver caches are cleared on every session-generation
boundary. Their write generations discard cache writes from earlier requests,
so a late old-account world/group response cannot repopulate or overwrite the
replacement account's positive or negative cache. Pending-resolution cleanup is
also generation-owned, so an old completion cannot erase a replacement
generation's same-id marker. `WorldResolver` additionally gives the newest
same-generation request for an id ownership of the cache write.

`credentialValidation.ts` is the shared, pure main-only guard for direct and issued authentication material (VRX-38). It permits Unicode direct-login text but rejects C0/DEL before either adapter makes a request; platform-issued VRChat Cookie and CVR Username/AccessKey values must be printable ASCII before use or persistence. It adds no renderer, IPC, or adapter-interface surface.

`importVrcxSession()` in `services/vrcxSessionImport.ts` is the VRX-54 main-only import boundary. It resolves the VRCX database from `app.getPath('appData')`, rejects symlinked or hard-linked source entries, verifies the expected database WAL mode, and makes a capped main-database snapshot below `app.getPath('temp')` only when no nonempty WAL, shared-memory lock, or rollback journal is active. The resolved temp and VRCX trees must be disjoint before any temp enumeration, creation, or removal. Because SQLite does not strongly bind an offline WAL to its main file, active sidecars are treated as running/locked VRCX: one transient retry, then `null`. Source aliases are rejected before open on every platform; platforms that expose `O_NOFOLLOW` and `O_NONBLOCK` receive those flags too. Header validation and `vrcxSnapshotCopy.copyOpenFile()` then read the same generation-bound source handle. The destination is created exclusively with no-follow semantics where supported, its handle remains open while SQLite parses its pathname, and the checkpointed private copy is switched to rollback-header mode so SQLite ignores snapshot WAL sidecars; destination handle/path plus snapshot directory/root generations are checked before and after parsing. Source file, VRCX directory, app-data directory, and sidecar generations are checked around the copy. This keeps SQLite-created files outside VRCX, closes path-alias, pathname-swap, and planted/substituted-destination races, and prevents stale/uncommitted cookie adoption. The snapshot root is atomically random-named and owner-only. Crash scavenging requires its exact generated-name form, VRX's private marker, and a recorded process that is no longer running before recursive removal. Unrelated prefix matches and active roots survive. The root is removed before persistence. The importer proves `cookies` is an ordinary rowid table with stored `key`/`value` columns, caps it at 64 rows, and uses metadata-only `octet_length()` to bound candidate keys and the unambiguous `cookies/default` value to 256 KiB before materialization. The base64 body must be fatal-valid UTF-8 before shape/header validation and `saveCredential`. Concurrent callers share one operation. It returns only `Promise<'imported' | null>`; VRX-35 still owns invocation and UI integration.

**ChilloutVR adapter** ([`CvrAdapter`](../src/main/services/adapters/CvrAdapter.ts), VRX-37/58/174) is now concrete and registered alongside VRChat. Parity notes: `login` (password → AuthType 2) and session validation (`getAuthStatus` → AuthType 1 reauth) both use the **breaker-free** `authenticateRaw` so validation failures can't lock out login; a dead key (401) clears the session everywhere; accessKey rotation is persisted; `getFriends` returns the roster (below), presence arrives via `subscribe` → `CvrPipeline`. Restored or imported credentials remain unavailable to authenticated REST and the live pipeline until one-shot validation and the owner-bound secure save both succeed; a save failure clears the restored session without publishing identity, sending account-data requests, or starting the pipeline. Success restarts the waiting pipeline without another auth request. CVR has **no 2FA** (`verify2fa` rejects; the future-2FA wiring seam is documented in `CvrAdapter.login`, VRX-229); `importSession` was removed from the adapter interface (VRX-221 sweep — nothing implemented it). VRX-56 instead imports only at the injected main-process credential-store boundary, so the adapter interface and renderer auth flow do not change. `getInstanceDetails` is LIVE via the VRX-59 instance resolver. Presence snapshots are enriched at the adapter boundary (see §6), and VRX-265 retains the last successful same-instance enrichment while a resolver TTL refresh is pending, while keeping each WebSocket frame authoritative for presence/privacy; a failed refresh drops the retained data and re-emits the wire fallback. Retained entries are pruned to the current full snapshot and cleared on account boundaries. `buildJoinUrl` emits the documented `chilloutvr://instance/join` contract with explicit desktop/VR selection; `selfInvite` unsupported. Session `{username, accessKey}` persists as one `safeStorage` blob (`CHILLOUTVR_PRIMARY`, shape-guarded); the password never persists/logs. When VRX has no valid stored CVR session, `cvrSessionImport.ts` checks read-only game and CVRX sources within one global second and fixed work budgets, rejects unsafe Electron roots plus Windows network/device candidates before source I/O, verifies file identity through a single capped handle, validates printable ASCII, and calls `saveCredential` before returning the imported pair for the existing one-shot AuthType 1 re-auth.

**WS clients:** [`ReconnectingPipeline`](../src/main/services/adapters/ReconnectingPipeline.ts)
is the shared lifecycle base (backoff, generation counter, `isOpen` send gate)
— **extend it, never fork it**. Concrete: `vrchat/VrcPipeline` (receive-only,
double-encoded envelope), `cvr/CvrPipeline` (header-auth, bidirectional
`sendFriendRequest`/`acceptFriendRequest`/`declineFriendRequest`/`unfriend`/
`sendInvite`/`requestInvite`/`block`/`unblock` — wired via `CvrAdapter.subscribe`,
VRX-58).

Production socket construction lives in
[`socketFactory.ts`](../src/main/socketFactory.ts). Both factories pass
`handshakeTimeout: API_TIMEOUT_MS` (about 15 seconds), while
`ReconnectingPipeline` remains transport-agnostic.

`useAuthFlow.externalTwoFactor` follows a mounted auth-status query into or out
of a restored-session 2FA reprompt and drops any typed password on entry. A
new reprompt selects the VRChat tab after any non-terminal active submit settles;
it does not remount away a terminal error on the selected platform. A failed
`LoginResult` with `sessionCleared: true` clears the submitted password and code,
synchronously writes known unauthenticated state to that platform's auth query
(no invalidation/network), and forces credentials on both LoginScreen and
AccountCard. App keeps LoginScreen mounted across that cache transition so its
dedicated or generic terminal error remains visible; tab/card remounts cannot
reseed stale `needs-2fa`. Other 2FA failures stay retryable on the code form,
and success remains the only path that invalidates auth status.
