# VRX 1.0 readiness

Checked on 2026-10-18 against `main` at `a95a2ff` (package version
`1.0.0-beta.1`). This is a point-in-time review, not a contract: the code,
[Releasing](RELEASING.md) and [AGENTS.md](../AGENTS.md) stay authoritative.

1.0 means the current feature set after a polish round, on Windows and Linux,
with no new features. Each item below says what to do, why, and what could
break. Items that need the owner's decision are marked **decision**.

## Must do before 1.0

Ordered by urgency.

### 1. Extend the audit exception before 2026-10-31 (deadline) — **decision**

`scripts/audit-policy.mjs:6` expires the `http-cache-semantics` exception at
`2026-10-31T00:00:00Z` (Oct 30, 7 PM Central). After that the `audit` CI job
fails, so `ci-success` fails on every PR and on `main`.

- Upstream still has no fix: npm shows 4.3.0 (2026-10-04) as the latest, and
  [SECURITY.md](../SECURITY.md) records that 4.3.0 does not fix the advisory.
  The package is build-tool only and does not ship in the app.
- Recommendation: extend it (as #376 proposes) in a small PR that changes
  the date in `audit-policy.mjs` and `SECURITY.md` together, merged before
  Oct 30. What could break: nothing in the app; the risk is only that the
  known dev-tool advisory stays accepted longer.

### 2. Make releases wait for CI — **decision**

Since #362, merging a version change to `main` publishes a release. The
release workflow (`.github/workflows/release.yml`) never checks CI, and its
build step runs only `npm run build` (typecheck + bundle), not lint or tests.
Branch protection on `main` currently has **no required checks**
(`required_status_checks.checks: []`, enforcement `non_admins`).

I agree with #376 that this is urgent, with one correction: requiring
`ci-success` in branch protection is not enough by itself. Enforcement is
`non_admins`, and the owner account (and every agent acting through it) is an
admin, so admin merges skip it. Also `workflow_dispatch` releases never pass
through a PR at all.

Recommendation, in this order:

1. In `release.yml`, add a gate job before `build` that confirms `ci-success`
   passed on the exact commit being released (and that the commit is on
   `main`). This covers admin merges, dispatch runs and manual tags.
2. Also require `ci-success` in branch protection, and turn on "include
   administrators" if the owner is comfortable not being able to merge red PRs.

What could break: a release run would wait for or fail on CI that is still
running; the gate must poll for the check rather than fail instantly.

### 3. Real-install acceptance pass

[RELEASING.md §5](RELEASING.md#5-public-10-acceptance-still-required) requires
a manual pass on a real Windows install (install, login survives restart, tray,
update from an older version, settings kept, uninstall, portable) and records
Linux as experimental until launch, credential persistence and update are
checked on a target desktop. Nothing in the repo records this as done.

Recommendation: cut `1.0.0-beta.2` after items 4 to 6 land, and use it for the
pass. Updating to it in-app also tests the updater. Record the result (date,
OS, what was checked) in RELEASING.md or the release PR so 1.0 has evidence.

### 4. ChilloutVR 403 signs the user out on data calls (parity bug)

`BaseAdapter.ts:158` turns any 401 **or 403** into an auth error, and
`CvrAdapter.ts` invalidates the session on that error in Explore
(`runExploreRequest`, ~line 535), the data path (~line 573) and background
instance enrichment (~line 894). VRChat does the opposite: `VrcAdapter.ts:956`
treats a 403 as "an ordinary denial on a live session, never an invalidation".

So a ChilloutVR "forbidden" answer (for example, a resource you may not view)
can log you out of ChilloutVR, while the same thing on VRChat does not. That
breaks platform parity and is a real usability bug. It is inferred from code;
I have not seen ChilloutVR return 403 on a live session.

Recommendation: agree with #376. Keep sign-out for 401 and for 403 on the
login/session-check calls; on data calls, re-check the session once and sign
out only if that check fails. Needs tests for both outcomes.

### 5. "Unofficial, not affiliated" notice in the app, for both platforms

[api-policy.md](api-policy.md) says VRX is unofficial and not affiliated with
VRChat or Alpha Blend Interactive, but the app UI and README show no such
notice. The setting `firstRunDisclaimerAcknowledged` exists in
`src/shared/settings.ts:70` but nothing uses it.

#376 proposes adding ChilloutVR's exact required sentence. I could not
independently confirm that sentence from the ChilloutVR terms, so check the
current terms text before relying on it. Correction to the proposal: a
ChilloutVR-only notice makes ChilloutVR look different from VRChat. Use one
short notice that names both platforms equally (and includes the exact
ChilloutVR sentence if their terms require it), on the login screen and in
Settings → About, plus the README.

### 6. Tell Windows users about the SmartScreen warning

If 1.0 ships unsigned (see below), Windows shows "Windows protected your PC"
on first run. [INSTALL.md](INSTALL.md) only says signing "must be checked"; it
does not tell a user what to do. Add a short section: click **More info**, then
**Run anyway**, and why it appears.

## Should do for 1.0 if small

### #368 Partial-platform failures are hidden

`combinedView` in `src/renderer/src/queries/friends.ts` reports an error only
when every platform fails, and the friends list shows it only when there are
no friends at all. If ChilloutVR fails while VRChat loads (or the reverse), the
user sees a silently partial list. #376 does not list this as a decision, but
it is a polish bug, not a feature, and it affects whichever platform fails, so
it matters for parity. Recommendation: a small, non-blocking "ChilloutVR
couldn't refresh · Retry" notice following the DESIGN.md feedback patterns.

### #369 CSP `unsafe-inline` for styles — **decision**

Agree with #376 that tightening the CSP is post-1.0 work (about 86 inline
styles). But the contradiction with AGENTS.md should not ship as-is: for 1.0,
amend AGENTS.md to record a style-only exception (scripts stay strict), then
tighten later.

## PR #379 (Vite 8 / electron-vite 6 / plugin-react 6)

CI is green on Windows and Ubuntu. Recommendation: **hold until after 1.0**.

- It replaces the bundler (Rollup → Rolldown) that produces every shipped
  file. Green CI proves the build and tests, not that the installed app starts,
  that the sandboxed preload loads, or that the IPC trust check accepts the
  packaged window. The PR itself lists these as unverified.
- 1.0 is a polish release. Vite 7 still works and nothing in 1.0 needs Vite 8.
- If the owner wants it in 1.0 anyway, it must ride a beta (beta.2) and get the
  full real-install pass from item 3, not just a merge.

Merging it would not publish anything (no version change).
