# 6. Main process

Part of the [internal API catalog](../INTERNAL-API.md). The code is the source of truth: read the file a row names before relying on it.

Main owns the privileged side of VRX: windows, credentials, sessions, platform traffic, persistence, alerts and game launches. [`index.ts`](../../src/main/index.ts) takes the single-instance lock and only then imports [`app.ts`](../../src/main/app.ts), the composition root. `app.ts` builds one `ApiAdmissionController` per platform, both adapters, the services below, the IPC handlers, the window, the tray and the updater, and disposes them on `before-quit`. The method contract every adapter implements is in [section 4](4-adapter-contract.md#4-platform-adapter-contract); renderer-facing handlers are in [section 2](2-ipc-channels.md#2-ipc-channels).

### App lifecycle and windows

| Symbol | File | Purpose |

| `UpdaterService` / `UpdaterServiceDeps` / `initAutoUpdater` / `getUpdaterService` / `applyUpdaterSettings` | [`updater.ts`](../../src/main/updater.ts) | Consent-based update state machine for packaged builds. `initAutoUpdater()` loads electron-updater lazily and returns one shared `Promise<UpdaterService>`; `app.ts` starts it `STARTUP_CHECK_DELAY_MS` (5 s) after startup, and `updater:check` starts the same load on demand. | `CHECK_INTERVAL_MS` / `MAX_JITTER_MS` / `NATIVE_STAGE_TIMEOUT_MS` | [`updater.ts`](../../src/main/updater.ts) | Re-check every 4 hours plus 0 to 30 minutes of jitter. On macOS a download counts as staged only after Squirrel confirms it within 5 minutes. |
| `isQuitShortcut` / `QuitShortcutInput` | [`quitShortcut.ts`](../../src/main/quitShortcut.ts) | Ctrl+Q without other modifiers. Windows and Linux remove Electron's default app menu (`Menu.setApplicationMenu(null)`), so `createWindow` quits on this key itself; macOS keeps its menu. |
| `AppStatusService` | [`appStatus.ts`](../../src/main/services/appStatus.ts) | In-memory per-platform WebSocket health and last REST reconcile time, served by `get-app-status`. Unknown health values record as `down`. |

`UpdaterService` follows the saved `updateChannel` (`updateFeed.ts`). Stable uses electron-updater channel `latest` with `allowPrerelease` and `allowDowngrade` off, so it never receives a beta, dev, or rc build. Beta and dev turn `allowPrerelease` on and leave `allowDowngrade` off. electron-updater already promotes its beta channel to a newer stable release. It only promotes the built-in alpha and beta channels, so dev uses `installDevStablePromotion` (`devReleaseFeed.ts`): that resolver walks the GitHub release list and `selectReleaseVersion` picks the greatest stable or `-dev.N` that is newer than the running build. A beta build is never a dev candidate, and an older release is never selected on any channel, including right after a channel change. Assign `allowDowngrade` after `channel`, because that setter forces downgrades on, then set it off again. A version outside the selected channel is ignored. Changing channel cancels an in-flight download and waits for that attempt to settle before the next check, so electron-updater cannot hand back the previous download. A disallowed build that was downloading or staged will not install on quit, and a late download event for one cannot install or replace an allowed offer. An installed beta or rc build stays on stable until the user picks a channel. electron-updater diagnostics are discarded rather than logged.

A damaged file is renamed to `accounts.corrupt-<time>.json` and the list starts empty (the next sign-in check records the account again); a file from a newer build, or one that could not be read, is kept and the list is read-only. |
| `CREDENTIAL_KEYS` / `CredentialKey` | [`credentials.ts`](../../src/main/services/credentials.ts) | The two allowlisted credential slots: `vrchat:primary` (session cookie) and `chilloutvr:primary` (username and access key as one JSON value). |

Rule: save after owner validation; no tokens to renderer. |
| `signOutCredential` / `isCredentialSignedOut` | [`credentials.ts`](../../src/main/services/credentials.ts) | Explicit sign-out writes a second marker that is never deleted, so an older build that still imports at startup knows the user signed out. The next save replaces it. |
| `CredentialEncryptionUnavailableError` | [`credentials.ts`](../../src/main/services/credentials.ts) | Thrown when OS `safeStorage` is unavailable, including Linux `basic_text`, which is never used. |
| `removeLegacyCredentialOwnerStore` | [`credentials.ts`](../../src/main/services/credentials.ts) | Best-effort startup deletion of the removed `credential-owners.json` sidecar (#371). Never throws. |
| `LOCAL_CREDENTIAL_PREFIX` / `encryptLocalCredential` / `decryptLocalCredential` | [`localCredentialEncryption.ts`](../../src/main/services/localCredentialEncryption.ts) | Fallback used by `credentials.ts` only when OS encryption fails: AES-256-GCM with a random installation key in a private `credential-storage` folder, a fresh nonce per write and the slot as associated data. Weaker than OS storage. Reading never creates or replaces the key; saving a new sign-in replaces a damaged key file with a fresh one, so one bad file can't block sign-in for good. |

Credential storage order: `saveCredential` tries OS `safeStorage` first and falls back to the local key only when OS encryption throws; filesystem and store failures still fail the login. Records written by the OS path are never reinterpreted locally. Both adapters re-save a restored session after validating its owner, which moves a fallback record back to OS storage when it becomes available.

`AccountRegistry` has no removal method. Entries in the `removed` state can exist only in files written by older builds; `listAccounts()` skips them.
