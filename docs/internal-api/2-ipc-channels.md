# 2. IPC channels

Part of the [internal API catalog](../INTERNAL-API.md). The code is the source of truth: read the file a row names before relying on it.

[`src/shared/ipc.ts`](../../src/shared/ipc.ts) is the single typed map: `IpcInvoke` (renderer asks, main answers), `IpcEvents` (main pushes) and `IpcNotifications` (renderer sends, no reply). Handlers live in [`src/main/ipc/`](../../src/main/ipc/), one file per domain. Add a channel only when no listed channel fits, and change the shared type, preload, registration, handler tests and this catalog together.

Rule (sender trust): [`registerIpcHandlers`](../../src/main/ipc/index.ts) is the only registration point. While the domain modules register, it wraps `ipcMain.handle` so each invoke runs [`isTrustedIpcSender`](../../src/main/ipc/security.ts) first, then the channel's rate limiter, then the handler. An untrusted sender gets `Untrusted IPC sender` and spends no budget. Each handler repeats the trust check and validates its request before use. The check admits only the exact Vite dev-server origin in development, or the top-level `out/renderer/index.html` document in packaged builds and built preview. Subframes and other local files fail. Registration removes electron-store's unused `electron-store-get-data` listener, and electron-log is imported from its Node entry (`electron-log/node`), which installs no IPC listener. The registered surface is exactly the 69 invoke channels below plus `renderer-hydrated`.

Rule (rate budgets): `IPC_RATE_LIMIT_BUDGETS` in [`rate-limit.ts`](../../src/main/ipc/rate-limit.ts) holds one timer-free sliding window per process and channel on a monotonic clock. `login`, `verify-2fa`, `import-session`, `logout` and `get-friends` keep one window per platform named in the request, so one platform's attempts or failing reads never block the other. A limiter fault fails open. An exceeded budget logs one `IPC rate limit exceeded` warning per window with the channel name only. Structured channels keep their result shape on denial: `login`, `verify-2fa` and `import-session` return `{ ok: false, needs2fa: false, error: 'rate_limited' }`, while `join-instance`, `join-explore-room`, `join-invite`, `self-invite`, `switch-avatar`, `answer-friend-request`, `send-friend-request`, `save-own-profile`, `set-home-world`, `set-world-rating`, `social-action`, `set-friend-note`, `sync-friend-note`, `set-alert-pick`, `set-favorite-friend`, `set-favorite-world`, `set-game-favorite`, `get-linked-profiles`, `change-linked-profile` and `test-vr-alert` return `{ ok: false, reason: 'rate-limited' }`, and `get-game-favorites` returns `{ state: 'rate-limited' }`. Every other invoke rejects with `rate_limited`. No denial carries retry timing or request data. These budgets are local; the platform wire limit is the admission queue in section 4.

The updater handlers delegate to `UpdaterService` in [`src/main/updater.ts`](../../src/main/updater.ts). The Explore handlers validate with strict Zod schemas (references 1 to 128 chars) and delegate to [`ExploreService`](../../src/main/services/exploreService.ts). The avatar handlers validate with strict Zod schemas and delegate to [`AvatarLibraryService`](../../src/main/services/avatarLibraryService.ts), or for `get-current-avatar` to [`CurrentAvatarService`](../../src/main/services/currentAvatarService.ts). The community handlers validate with strict Zod schemas and delegate to [`CommunityService`](../../src/main/services/communityService.ts). `set-home-world` uses the Explore reference schema and delegates to [`HomeWorldService`](../../src/main/services/homeWorldService.ts). `get-world-rating` and `set-world-rating` use that same reference schema and delegate to [`WorldRatingService`](../../src/main/services/worldRatingService.ts). The social handlers do the same for [`SocialActionService`](../../src/main/services/socialActionService.ts). The own-profile handlers validate with strict Zod schemas (a failed `save-own-profile` parse answers `invalid`) and delegate to [`OwnProfileService`](../../src/main/services/ownProfileService.ts). The friend action handlers validate with strict Zod schemas and delegate to [`FriendActionsService`](../../src/main/services/friendActions.ts).

`get-friends` ordering: the handler runs `createFriendRosterReader`, the same read main runs after a reconnect while no window is open. It captures a `LocationAuthority` seed revision before the read, seeds the authority from each physical read in `FriendRoster.seeds`, records the reconcile time in `AppStatusService`, and hands `FriendAlerts.seedRoster` the authority's merged rows, so a live removal that landed during the read wins. VRChat responses add `provenance`: `baseRevision`, deduplicated `coveredIds` for a partial read, and `overrides` naming rows replaced by a follow-up read. Rule: only a `complete` roster may reconcile missing friends; a partial result keeps cached omissions.

`join-instance` checks, in order: request shape (target ids up to 2,048 chars), the `allowJoinInstances` setting (`joining-disabled`), main's current location for the friend (`unknown-friend`, `stale`), `isFriendJoinable` (`not-joinable`), `expectedTarget` against the current target (`target-changed`), `adapter.buildJoinUrl` passing `isAllowedLaunchUrl` (`invalid-url`), a [`JoinCoordinator`](../../src/main/services/joinCoordinator.ts) permit with one launch per platform at a time and a 3 s destination and friend cooldown (`cooldown`), and finally [`GameHandoff.deliver`](../../src/main/services/gameHandoff.ts): launch through `shell.openExternal` (`launch-failed`), or reach the game that is already open (VRChat URL pipe, else one `adapter.selfInvite`, `invite-failed`). The account fence is checked again after every wait, including right before the pipe write (`stale`). Success carries `handoff`. Denial logs carry platform and reason only. `join-explore-room` shares the same coordinator, launch validation and hand-off (`ExploreServiceOptions.deliverJoin`).

`join-invite` checks, in order: request shape, the `allowJoinInstances` setting (`joining-disabled`), `InboxService.inviteTarget` for the row (`stale` when the row is gone, hidden, another account's, not an invite, or named no well-formed instance), `adapter.buildJoinUrl` passing `isAllowedLaunchUrl` (`invalid-url`), the account fence (`stale`), a `JoinCoordinator` permit keyed by the destination and the sender (`cooldown`), then the same `GameHandoff.deliver` as `join-instance`. The row stays after a Join, and nothing is sent to the sender. Denial logs carry platform and reason only.

Linked-profile lease: [`links.ts`](../../src/main/ipc/links.ts) issues a random lease that rotates whenever either platform's `AccountSession` resolution changes. A snapshot holds only profiles with a member owned by a currently ready account, plus `accountIds` for those ready accounts. `change-linked-profile` validates strictly (ids match `[A-Za-z0-9_-]+`, names up to 256 chars, shared note up to 500 chars after trimming), returns `stale` for an old lease, requires one friend per platform with both accounts ready for `replace` (`unavailable`), qualifies members with main's account ids, and applies through [`LinkGraphStore`](../../src/main/services/linkGraphStore.ts) with revision checks. Failure reasons are `invalid`, `stale`, `unavailable`, `storage` and `rate-limited`.

## Push channels (main broadcasts, renderer listens)

Rule: push channels go from main to renderer only and are never registered as invoke handlers. Main sends each push to every non-destroyed window. Preload removes the listener on unsubscribe.

There is no notifications channel. Friend, hot-instance and inbox alerts are native main-process notifications ([`friendNotifications.ts`](../../src/main/friendNotifications.ts), [`friendAlerts.ts`](../../src/main/services/friendAlerts.ts), [`inbox.ts`](../../src/main/services/inbox.ts)), gated by settings at dispatch. With `vrOverlayAlerts` on, the same alerts also go to XSOverlay in the VR headset ([`vrOverlayAlerts.ts`](../../src/main/vrOverlayAlerts.ts)): one UDP datagram from a socket bound to `127.0.0.1` to XSOverlay's port 42069 on `127.0.0.1`, then the socket closes. Clicking a hot-instance alert focuses the window and pushes `navigate-to-dashboard`; other alerts only focus the window. Invites, invite requests and friend requests from both sockets reach the renderer only through `get-inbox` and `inbox-changed`, never `friend-event`. `src/shared/ipc.ts` names `launch-app` as a deferred channel with no types or handlers.
